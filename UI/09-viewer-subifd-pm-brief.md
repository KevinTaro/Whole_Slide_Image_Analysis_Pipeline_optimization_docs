# viewer 影像格式（subifd）— 給資工 PM 的討論

> 對象：資工 PM（有工程背景、非影像領域）
> 目的：說明「為什麼 viewer 一定要用 `subifd=False` 副本」，並列出需要拍板的決策。
> 技術細節全貌見 [`09-viewer-tiff-subifd.md`](09-viewer-tiff-subifd.md)；本篇是決策導向的摘要。
> 日期：2026-07-09

---

## TL;DR（一句話）

pipeline 產出的病理影像 TIFF，為了餵配準引擎 VALIS，一律是 `subifd=True` 格式；但這種格式
直接丟給前端 viewer（OpenSeadragon / OpenSlide）會讓後端讀圖時把整張原尺寸攤開、**瞬間吃爆記憶體
當掉**。解法是**另存一份 `subifd=False` 的 viewer 副本**給前端用——實測轉一張只要 **2 分鐘、2 GB**。
需要 PM 拍板的是「這份副本由誰、在哪一環產」以及「要顯示哪些圖」。

---

## 1. 背景：為什麼原檔是 subifd=True（這不是 bug）

- WSI（全切片影像）是「同一張圖的多解析度**金字塔**」。看圖時前端只抓「當下縮放層級 + 可見範圍」
  的小塊（tile），所以幾十 GB 的圖也能流暢瀏覽——**前提是金字塔讀得到**。
- 金字塔各層在 TIFF 檔裡可以兩種擺法：一般 IFD 鏈（各層平列）或 **SubIFD**（各層藏在主層的子目錄）。
- 我們的配準引擎 **VALIS 回讀金字塔只認 SubIFD**，所以 pipeline 產出的檔一律 `subifd=True`。
  **這是既有且正確的設計，是演算法的硬需求，不是誰寫錯。**

## 2. 為什麼 viewer 不能直接用 subifd=True

- 前端 viewer 走 **OpenSlide** 讀圖，而 **OpenSlide 不鑽 SubIFD**：看到 subifd=True 檔會回報
  「只有 1 層」（金字塔形同不存在）。
- 於是前端要顯示「縮小的概覽」時，後端被迫從**原尺寸**即時降採樣——單張概覽 tile 要讀十幾 GB。
  viewer 為填滿畫面會**同時併發**抓一整排這種 tile → 記憶體瞬間爆掉 → 後端 process `MemoryError`
  當掉（**連帶把同時服務中的其他圖一起停**）。
- 實測（同一張約 16 gigapixel 圖）：
  - subifd=True：首屏 tile **8.6 秒**，再縮一級直接 **OOM 當機**。
  - subifd=False：首屏 tile **23 ms**，全程平坦、不爆。

## 3. 為什麼 viewer 要用 subifd=False（且不能直接改掉原檔）

- subifd=False（一般 IFD 鏈）OpenSlide 讀得到**完整金字塔**（實測 `level_count` 從 **1 → 11**），
  每個 tile 只讀對應層的 ~500px，又快又不爆。
- **但不能把 pipeline 直接改成 subifd=False**——那樣 VALIS 會壞（它回讀就是靠 SubIFD）。
- 所以結論是**兩份並存**：演算法端維持 `subifd=True`（VALIS 用）；**額外**產一份 `subifd=False`
  副本（viewer 用）。**副本是加法，不是取代。**

## 4. 成本（實測 2026-07-09，真實對齊輸出）

轉一張對齊圖（來源 19.3 GB、155807×133474）→ `subifd=False + tiled` 金字塔副本：

| 指標 | 值 |
|---|---|
| 轉檔時間 | **2.09 分鐘 / 張** |
| viewer 副本大小 | **2.03 GB**（約來源 1/10，白底壓得好） |
| OpenSlide `level_count`：來源 → 副本 | **1 → 11** |

三張全轉約 **6 分鐘、~6 GB**。是**一次性後處理**，不影響看圖當下效能（反而讓看圖變快）。
→ 成本極低，**不構成效能或容量顧慮**。

## 5. 需要 PM 決定的事

1. **副本由誰、在哪一環產？**
   - **(a)** 後端/UI post-step：tile server 偵測到 subifd=True 就自動轉一份（不碰演算法）。
   - **(b)** 演算法 pipeline 在主輸出之外**多吐一份** viewer 副本（主輸出仍 subifd=True）。
   - **(c)** 換掉後端讀圖器（改用會鑽 SubIFD 的 reader，如 pyvips/tifffile），理論上免副本，
     但要動後端讀圖核心、成本高且**未驗證**。
2. **顯示範圍**：要顯示的是「**合併疊合圖**（Merged_Aligned，單張）」還是「**三個對齊分層**可調
   透明度疊圖」？前者只需轉 1 張、後者需轉 2–3 張。（roadmap 主線寫的是「看疊合圖」。）
3. **責任與排期**：這是 **7/9 才發現**的需求，晚於原始 UI 規劃（7/2–7/4）與甘特圖，目前只在
   甘特圖**備註**、沒有任務列/負責人/週次。要不要正式排進計畫。

## 6. 我的建議

- **短期先讓 UI 能開圖**：(a) 或 (b) 皆可。成本這麼低（2 分 / 2 GB），我傾向 **(b)**——pipeline
  跑完順手多吐一份 viewer 副本，UI 端零負擔、拿到就能顯示。
- **(c) 免副本方案不建議現在做**：雖然架構乾淨，但要動後端讀圖核心且未驗證，風險/工時不划算。
- **把它補成甘特圖的一條正式任務**（負責人 + 週次 + 對應 Phase），別讓它只躺在備註。
