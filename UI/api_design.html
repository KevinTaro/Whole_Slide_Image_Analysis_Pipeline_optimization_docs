Q1 · API 全部走 localhost，上雲要改什麼

結論

優先維持 same-origin，把「網路邊界」交給 reverse proxy；認證從「不需要」變成「必須」。

現況 vs 建議

  • Uvicorn 不直接對外，前面掛 Nginx／Caddy／雲端 ALB 做 TLS termination。
  • 前後端同 origin，client.ts 現有「只打相對路徑 /api/*」的假設幾乎不用改；只有前後端真分開部署才需要 API_BASE_URL + 嚴格 CORS allowlist。
  • 每個 slide_id／job_id／tile 請求都要做 ownership 檢查，不能只驗證「有沒有登入」。

Q2 · 長任務（以小時計）的健康 / 錯誤回報

結論

現有 BackgroundTasks + 記憶體 dict 是為單機單使用者設計的最小方案，一旦變共用伺服器就會直接失效，需要換掉。

失效原因 1

同一 process

長任務跟 API 共用 process，Uvicorn 重啟／部署新版會把跑到一半的任務直接殺掉。

失效原因 2

記憶體 dict

重啟即歸零；若之後開多個 worker/replica，使用者建立的 job 換一台查詢就會 404。

失效原因 3

沒有 heartbeat

現有四態 schema 分不出「還在跑」跟「process 已死、卡死在 running」——正是本題要回答的問題。

建議新增：Postgres Redis RQ / Dramatiq Reconciler —— job 狀態存進資料庫取代 dict，運算搬到獨立 worker，中間用佇列（AWS 上等價於 SQS + worker service）。複雜度是「長任務撐過重啟/多副本」的最低必要成本，不需要一開始就上 K8s 等級編排。

GET /api/jobs/{id} 回答「這個任務」的狀態；/health/* 回答「這個服務本身」死活——兩者現在被混在一起想，實務上要分開。輪詢機制本身不用換成 WebSocket：成本跟是不是單機無關，真正要換的是「狀態存在哪」跟「誰執行」；未來要做即時進度條，SSE 仍是對的升級路徑。

Q3 · 上傳 → 計算 → 結果，資料存哪、回傳什麼

結論

後端持久化所有資料，前端永遠只拿輕量 metadata 與 tile / 結果連結——延續現有護欄 7 的精神。單機部署（單一 EC2 或院內單一 VM + 掛載磁碟）下，這就是現有桌面版架構原封不動搬過去，不需要物件儲存。

不建議：寫回使用者端原始檔

HTTP 是 client 主動發起的協定，伺服器無法主動寫入瀏覽器另一端的本機硬碟；要做到得另外裝 client agent／掛網路磁碟，會讓現有「前端看不到本機路徑」的護欄 2 失去意義，且 WSI 動輒幾十~幾百 GB，寫回等於整檔再搬一次。

建議：伺服器端持久化 + 只回結果

沿用現有「大檔案留在後端、HTTP 只傳輕量資料」的護欄，只是把「backend 檔案系統」從筆電換成 EC2（或院內 VM）掛載的磁碟——同一台機器收檔、算、serve tile，跟現在完全同一種形狀，不需要另外導入物件儲存服務。

資料流（單機部署）
flowchart LR
    C["瀏覽器"] -->|"① chunked 上傳（TUS）"| BE["Backend（EC2 / VM）"]
    BE -->|"② 寫入本機磁碟"| FS[("磁碟（EBS 或本機硬碟）")]
    FS -->|"③ 檔案路徑 + JSON"| ALG["algorithms/ 演算法"]
    ALG -->|"④ 結果檔 + JSON"| FS
    FS -->|"⑤ tile / metadata"| C

上傳側（現況完全沒有，全新增）：WSI 幾十~幾百 GB，不適合一般一次性 multipart/form-data。用 TUS 協定（或等價的自訂 chunked endpoint）把檔案切塊直接 PATCH 進 backend，backend 寫進本機／掛載磁碟即可——單機部署不需要 presigned URL、不需要物件儲存的分塊上傳協定，backend 自己就是唯一的儲存端。

Tradeoff / 風險

合約層級

雲端 vs 院內自架

雲端牽涉資料落地、BAA、金鑰管理、稽核；院內自架要自扛備份與勒索軟體應變。必須回到第 0 節先確認。

維運成本

佇列 + 資料庫

新增維運負擔，但沒有它任務撐不過一次重啟。單機部署下 worker process + Postgres 可以先跟 API 擠在同一台 EC2 上，不需要獨立服務或多副本。

資料真實度

進度回報

若 pipeline 內部跑在沒插樁的原生呼叫裡，寧可回粗顆粒 stage 或 null，也不要編造精確百分比。

單機風險

單點故障 + 磁碟容量

單一 EC2 沒有物件儲存的自動備援，磁碟滿了任務會直接失敗；需要磁碟用量告警 + EBS snapshot 排程備份，不是「上雲就自動有備份」。

授權責任

上傳仍要驗身份

單機直傳省掉了 presigned URL 那層，但也代表 backend 自己要在 PATCH /api/uploads/{id} 驗證上傳者、配額、checksum，不能假設「能連到這台機器」就等於「有權上傳」。

資訊洩漏

result_path / str(e)

本機模式下無害，上網路後就是路徑外洩／內部錯誤訊息外洩，已在第 2、3 節草案中改掉。
