「我的 API 到底傳圖片還是傳路徑?」

前提變更:前端與後端不再是 localhost,而是分屬兩台機器(內網 / EC2),單機單用戶。

討論模型 gpt-5.6-sol · effort high · 2026-07-19

一句話結論:現在你的 pipeline API 兩個都不是「傳圖片」——它傳 id 進去、傳路徑字串出來,圖片像素只在「看圖」時才過網路。而「回傳路徑」正是拆成兩台機器會斷掉的根因。

跨機器後正確答案是:路徑整個消失,圖片只在頭尾兩端當 bytes 傳(上傳、下載/看圖),中間全部用 id。

0核心問題:你的 API 現在傳什麼

會混淆,是因為現在有三條完全分開的通道被當成同一件事。逐條拆:

通道方向實際傳的東西證據(檔案:行)
跑 pipeline 前端 → 後端 id 或空 body,沒有圖片 PipelinePanel.tsx:43 alignment 送 body:{};:66 hybrid 送 {ihc_slide_id, dish_slide_id}
拿結果 後端 → 前端 一個路徑字串 result_path jobs.py:33 存 result_path;PipelinePanel.tsx:202 把它當文字印「結果:{path}」
看圖 後端 → 前端 真正的 jpeg bytes SlideViewer.tsx + tiles.py:35,OSD 按 slide_id 逐塊抓圖磚

換句話說:整條 pipeline API 從頭到尾沒有一張圖片過網路。圖片本來就躺在後端自己的硬碟(SLIDES_DIR),前端只是叫後端「處理你自己硬碟上那個東西」,後端再回「結果在我硬碟的這個路徑」。

為什麼拆兩台一定壞:前端在你的電腦、後端在 EC2,兩顆硬碟不再共用 ——

  • 後端看不到你電腦上的輸入檔 → 「跑 pipeline」沒東西可處理。
  • 後端回的 /home/ubuntu/output/Metrics.csv 在你電腦上不存在 → 你拿到一個廢字串。

順帶一個現在就對不上的 bug:frontend 送 ihc_slide_id/dish_slide_id(PipelinePanel.tsx:67),但後端 HybridTileIn 收的是 ihc_path/dish_path(schemas/hybrid.py:12)。欄位名對不上,hybrid 其實現在就是壞的。

1跨機器後的正確資料流

核心規則只有一句:路徑永遠不出後端。像素在兩個時刻以 bytes 過網路(上傳、看圖/下載),中間全部用 id。

你原本以為是「圖片 or 路徑」二選一。真正的答案是:路徑要整個消失,圖片只在頭尾兩端當 bytes 傳。

2單機單用戶:能砍掉什麼

「一台機器只服務一個人 + 內網/EC2 + 單 peer 身分即可」這幾個前提,砍掉了整層多租戶與認證。真正即使單用戶仍必須保留的只有「禁止傳路徑、大檔可續傳」——那是「遠端 + 大檔」的需求,不是「多人」的需求。長任務與 job 狀態則沿用現有的 BackgroundTasks + 記憶體 dict 就夠(理由見下方 SQLite 註記)。

元件判定單機單用戶版本
OIDC / 登入 / token / session移除網路邊界交給 EC2 Security Group(只開你的來源 IP)/ 內網防火牆,應用層不做登入
使用者表 · owner_id · ACL移除整台 instance 即單一資料域,查詢不再帶 WHERE owner_id
tiles.py owner filtering移除直接列出本機所有已登錄 slides
備份 · retention 清理 · 磁碟門檻移除容量當無限;只留一支「使用率 > 80% 印 warning」
per-user 配額 / 公平排程移除單一 FIFO worker 自然序列化
Redis + RQ / 獨立 task queue移除單用戶一次一個 job,不需要外部佇列 —— 沿用現有的 BackgroundTasks
asset_id + artifact_id 兩套 ID簡化統一成一個 file_id;上傳直接存成 {file_id}.ext,file_id 即檔名,連 catalog 表都不用
「API 不接受路徑」+ 不透明 handle保留防跨機器語意失效 + 任意讀寫檔案的攻擊面
長任務用 BackgroundTasks(現況)保留anyio threadpool 已把運算移出事件迴圈,輪詢照常回應;重啟中斷 = 重跑(你接受的模型)
job 狀態 · polling保留現況in-memory _jobs dict + 輪詢就夠;「已完成結果撐過重啟」屬 optional,痛了再加 SQLite
tusd 大檔續傳 · Nginx protected download保留多 GB WSI/TIFF 過 WAN,不能塞單一 request、不能占 API worker
結構化錯誤 / 分層 timeout保留遠端 + 長任務仍需區分「排隊逾時 / 執行逾時 / 壞輸入」

關於 SQLite —— 為什麼這版拿掉了。先前草案把 SQLite 當必需品,其實它的兩個角色都有更省的替代:

  • file 目錄:上傳存成 {file_id}.ext,file_id 本身就是檔名 —— 查表 = 字串拼接,不需要資料庫。
  • job 狀態:in-memory dict 就夠。重啟中斷的計算 SQLite 也救不回來(記憶體裡的運算沒了就是沒了),只能 raise error 重跑 —— 這正是你說的作法。

SQLite 唯一真正賺到的場景:一個長任務算完了、使用者離開,這時後端因部署/維護重啟,記憶體版會讓已完成的結果憑空消失、得再等一次。這是「痛了再加」的 optional,不是第一天的必需品。

3最小骨架

砍完之後剩下的骨架——沒有 VPN、認證、owner、備份、配額、retention,連資料庫都不用:

對應改動範圍

  • schemas/alignment.py · schemas/hybrid.py:拿掉所有 *_dir / *_path 欄位,改收 file_id。
  • api/jobs.py:幾乎不動 —— 沿用 in-memory _jobs dict + BackgroundTasks;只把存的 result_path 改成 file_id。
  • 新增:tus 上傳端點,收到的檔案存成 {file_id}.ext(file_id 即檔名,不建 catalog 表)。
  • frontend:result_path 顯示改成「下載連結 / 開啟 viewer」;hybrid 欄位名對齊(*_slide_id ↔ 後端 *_path 目前對不上);新增上傳 UI。
  • main.py:掛 Nginx protected download 的 internal redirect 端點(多 GB 結果檔不佔 API worker)。

4部署前仍必須決定的取捨

  • frontend 是否為 HTTPS origin:若是,API 也要 HTTPS,否則瀏覽器擋 mixed content。
  • job 被中斷後:標記 failed 由人重送(推薦),還是做 checkpoint/resume(每條 pipeline 狀態設計大增)。啟動 reconciliation 要把殘留的 running 標成 interrupted/failed,不自動重跑。
  • 各 pipeline execution timeout:依實測設,不可套短任務預設,也不建議 unlimited(否則失控工作長期占住唯一 GPU)。
  • Idempotency-Key / 防連按兩次:相同 dataset+stage 已在 queued/running 時要不要直接拒絕重複提交。

5下一步

建議先動「根」:移除路徑參數 → 改 file_id(檔名即 id)+ tus 上傳。這塊不落地,其他(下載、看圖)都接不上。job 與 worker 沿用現有的 BackgroundTasks + 記憶體 dict,先不碰;等真的被「重啟掉已完成結果」咬到,再把狀態換成 SQLite。
