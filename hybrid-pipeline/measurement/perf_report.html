2 · Method & execution order (plan §1.4)

Non-invasive harness (scripts/perf_measure.py): the pipeline is run unchanged; timing shims are monkeypatched onto the hybrid_pipeline module namespace, plus a 0.5 s RAM/VRAM sampler thread and 1 s nvidia-smi dmon. Order follows the plan: (1) measure one clean end-to-end wall-clock anchor first (no cProfile — cProfile inflates the Python-heavy items), (2) that serial run is itself the "dumb-version" control (run_batch is a hard-coded sequential loop), (3) every sub-item is divided by the anchor to get % before looking at absolute seconds. A separate cProfile pass supplies the function-level Top table only.

Input scales (all real, from the 156222×134028 warped WSI pair): 25-tile (4096² test ROI), 121-tile (8192² crop), 441-tile (16384² crop). A full-WSI run = 35,700 tiles (~20 h) is projected, not run.

5 · Cross-cutting: GPU utilization timeline, RAM/VRAM (plan §4)

The headline finding. Across every scale the GPU is idle ~48–59% of wall-clock with mean SM utilization only ~24–29%, even though this is the sole GPU workload. The serial run_batch loop interleaves GPU forward passes (B1) with CPU-bound detect_all_dots (B3), PNG encode (B2) and per-tile gc.collect (B4); while any of those run, the GPU stalls. B1's ~48% wall share is therefore elapsed time that includes inter-forward gaps, not 48% GPU saturation.

The new architecture's "memory bounded, not linear in tiles" claim holds under real large input. VRAM has huge headroom — the fixed batch_size=16 leaves the 5090 heavily under-filled.

5.1 Adjacent-phase supply vs consume (plan §4.7)

  • A → B: strictly serial by construction — precut_paired_tiles() runs to completion, then run_batch() starts. Zero overlap; precut wall adds directly on top of analysis. Precut writes all tiles with an 8-thread pool (pyvips releases the GIL) and stays ~2.3% of wall at every scale, so it is real parallel I/O but a small slice.
  • within B, GPU vs CPU: the true "looks-parallel-but-serial" trap — three models share one CUDA context and run one tile at a time; per tile, GPU forward and CPU dot-detection execute in sequence, so neither the GPU nor the 20 CPU cores are ever saturated at the same time. This is the ~48% GPU idle.
  • B → D: serial. _stitch_overlay_slide() runs only after all tiles are analyzed; it is a single non-parallel pyvips join+lzw+tiffsave. Measured ≤0.75% of wall at every scale (read+join+compress are fused inside one tiffsave C call and cannot be separated by Python-level timing).

8 · Doc/code/config gaps found (kept out of the perf conclusions)

  • G-A · WSI tile count off by ~28×. Plan/03-doc say the full WSI is "1287 tiles (39×33)" — that assumes 4096px tiles. The pipeline's actual default_tile_size=1024 (stride 768) on 156222×134028 gives 204×175 = 35,700 tiles. All full-WSI extrapolations must use 35,700, not 1287.
  • G-B · cellpose_batch_size still dead. Confirmed on HEAD: config_example.py has no cellpose_batch_size field; both segmenters use getattr(config,"cellpose_batch_size",16) → hard-wired 16. Any batch-size sweep needs the field added first (plan §2.5). VRAM headroom (5/32 GB) shows 16 under-fills the 5090.
  • G-C · requirements.txt missing deps. segmentation_models_pytorch (M1 UNet), fastapi, uvicorn are imported but absent from requirements.txt.
  • G-D · torch cu130 wheel install path. R2 CDN TLS failure on this host; documented workaround in §1.
  • G-E · config_example G2 gotcha resolved. Old docs flagged a missing compute_config_hash()/config=Config() tail — present and working on this HEAD.
