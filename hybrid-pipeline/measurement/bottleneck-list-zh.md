## 深入分析候選項（貢獻度不可忽略）

### ① GPU 未充分利用 — 源自完全串列管線 — **首要問題**
| 欄位 | 說明 |
|---|---|
| 現象 | GPU 閒置 **~46–49%** 時間（大規模：idle_frac 0.459），平均 SM 使用率 **~28%**，即使是唯一的 GPU 工作。B1 前向傳播 = **牆鐘時間的 45.5%** = 三個串列前向傳播/地磚（M2 Cellpose + M3b Cellpose + M1 UNet）共享一個 CUDA 上下文。VRAM 峰值 **5.16 / 32 GB**（batch_size 硬編碼 16）。|

| Amdahl 天花板 | 1.84（B1 階段）— 但真正的槓桿是閒置，而非 B1 運算 |
| 所在階段 | B1（× 跨層 §4.1/§4.7） |
| 量測規模 | 25/121/441 地磚 — 區間穩定（閒置 0.49→0.48→0.46） |
| 新發現 | 舊 03/04 文件 *懷疑* GPU 飢餓但未驗證；**今已實測** |
| 分類方向 | **Class 3（平行/並行）+ Class 6（架構）**：串列 `run_batch` 迴圈、無跨地磚 GPU 批處理、模型從未與 CPU 工作重疊 |
| 信心度 | 實測直接量測（measured directly） |
- **更新（方案 (b) 已落地 → 單程序雙階段重疊）**：`run_batch` 現在會把每個地磚的 GPU 前段，和上一個地磚的 CPU 後段重疊執行（背景執行緒，深度 1）。實測效果：GPU 閒置比率 0.494 → 0.154，121 地磚牆鐘時間 −18.5%；見 [`pipeline-overlap-result.md`](./pipeline-overlap-result.md)。重疊之後，GPU 前段（M1 UNet + M2/M3b Cellpose 前向）現在已是 **441 地磚時佔 80.9% 牆鐘** 的主關鍵路徑，而它本身的最佳化（① 下一階段，CuPy/GPU kernel）才是剩下的槓桿，這裡不展開。這也正是 **② 變成被重疊遮蔽** 的原因（見 ② 的交叉驗證）。

## Amdahl 下限以下的項目（已記錄但本輪未深入分析 — 方案 §5.2）

### ④ 每地磚 `gc.collect()` — 地磚邊界清理
- **36.3 秒 = 4.28%**，天花板 1.04。完全由 `run_batch` 中每地磚執行一次的顯式 `gc.collect()`（`torch.cuda.empty_cache` 另計 < 0.3%）。每地磚進行一次完整 Python 垃圾回收掃描是固定開銷，與地磚數線性相關。**從未量測過**。Class 4（記憶體生命週期）+ 6（框架）。信心度：實測。

### ⑤ 階段 A 預切（2.43%）& 階段 D 疊合拼接（0.60%）— 新增階段
- 兩個全新階段是舊效能報告從未涵蓋的。預切 A ~2.4%（每個規模都是，真實 8 執行緒平行 I/O，pyvips 釋放 GIL）。拼接 D ~0.6% — 所有分析後單次串列 `pyvips` join+lzw+`tiffsave`（讀取+join+壓縮在一個 C 呼叫中融合，不可由 Python 計時分離）。在完整 WSI 時，D 成為單次串列約數分鐘的塊，但仍 < ~19 小時執行的 1%。Class 5（I/O）；D 亦 Class 3（串列，可與分析重疊）。信心度：實測 + 外推。

### ⑥ 模型初始化（一次性）
- 25 地磚時 7.3% → 121 時 1.3% → **441 時 0.37%**。純一次性載入，在 WSI 規模時攤銷至可忽略。Class 6。資訊性。信心度：實測。
- **交叉驗證（2026-07-08，第二階段 GIL 診斷）**：這個一次性成本就是 [`gil-contention-diag.md`](./gil-contention-diag.md) 原始 Result 1 表格中「UNet++ Python 14.9%」被放大的原因之一，其中 93% 的 GIL 區塊其實來自 `_init_unet_inferencer` 的匯入鏈（`segmentation_models_pytorch` / `torch` / `timm` / `torchvision` / `triton`），而不是每地磚重複成本。這同時確認此項「在規模下可忽略」，並排除 UNet++ 是每地磚 GIL 來源；完整追蹤請見該文件的「追加深挖」段落。

### ⑦ API / 工作層（階段 E）
- `submit_job` 入隊 **2.3 µs** 平均；BackgroundTask 派遣 **~3.8 ms** — ~10⁻⁷ 多小時執行的時間。可忽略。唯一注意事項：並行分析請求各佔用一個執行緒池工作者，但在單一 GPU/CUDA 上下文上序列化（未來多請求風險，非當前熱點）。Class 6。信心度：實測。

## 記憶體成長聲明驗證（方案 §3.6 / §4.3）
- **VRAM**：所有規模下平坦 **5.16 GB / 32 GB** — **不** 隨地磚數增長。✔ 有界。
- **RSS**：2.82 → 3.07 → 4.04 GB（跨越 25 → 121 → 441 地磚，17.6× 地磚，+43% RSS）— 顯然 **對地磚數次線性**，但非完全平坦：追蹤 **總累積細胞結果**（`per_tile_owned` 存於 RAM 直到最終全域合併），即隨細胞數增長而非地磚數。新架構「記憶體有界，不隨地磚線性」的聲明 **成立**；殘差成長由細胞數驅動，非已刪除的 400 GB 畫布。
